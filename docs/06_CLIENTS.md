# 06 各客户端实现说明

> [!IMPORTANT]
> 实际员工操作只使用为 Samsung 安卓平板设计的 Android App。`front_admin/` 不投入现场使用；`windows_employee_app/` 不再更新员工交互功能，但继续作为固定小票打印工作端。顾客网页和经营管理网页属于其他角色，不受此限制。

## 1. 顾客手机网页 `front_user/`

### 1.1 目标

让顾客无需安装 App，通过包厢二维码进入已开台包厢、输入姓名、点单和查看进度。页面使用原生 HTML、CSS、JavaScript，没有打包步骤。

### 1.2 页面状态

`front_user/app.js` 维护：

- 当前二维码 token；
- 区域和菜单；
- 分类分组；
- 个人购物车和备注；
- 同区域其他顾客的实时购物车；
- 顾客 session；
- 轮询与 UI 状态。

顾客 session token 按区域 token 存入 `localStorage`，刷新页面后可尝试恢复。服务端仍会重新验证是否开台、是否过期和是否被撤销。

### 1.3 主要交互

- 显示店名、区域和菜单分类；
- 输入姓名并在员工开台后建立顾客 session；
- 增减菜品；
- 编辑备注；
- 查看小计、13% HST、18% 服务费和总计；
- 查看本区域实时购物车；
- 提交订单；
- 查看本访问周期内提交的订单及状态。

页面定时刷新上下文、购物车和订单。网络失败时主要通过页面消息提示，没有离线下单队列。

Access Code 已退役：顾客页必须移除输入框、提示、校验分支和请求字段。除这项窄范围退役外，本轮不重构顾客页。

### 1.4 关键边界

- token 来自 URL，但真正写操作仍依赖顾客 session；
- 所有价格以服务端下单重算为准；
- 页面展示英文为主，区域标签会做 Room/桌台格式化；
- 根路径没有 token 时只能打开页面，不能形成有效点单区域。

## 2. 员工 Web 看板 `front_admin/`（保留但基本不使用）

### 2.1 目标

这是仓库保留的浏览器员工看板，不是正式现场员工端。本轮不得为了多端一致性同步重做它，也不能用浏览器验证代替 Samsung 平板验证。

### 2.2 功能

- 员工登录/退出；
- 订单状态筛选；
- 新单提示音；
- 中英文界面；
- 按 FIFO 时间排序展示订单；
- 更新订单状态；
- 标记菜品已送；
- 调整菜品数量；
- 给活动订单加菜；
- 查看每个区域会话及结算状态；
- 开台；
- 切换分开/合并账单；
- 标记顾客已结；
- 结单清零；
- 显示服务端写队列状态。

员工 token 保存在浏览器本地存储。接口返回 401 时客户端会清除本地会话并要求重新登录。

### 2.3 与经营管理页的区别

员工看板处理“正在发生的订单”；`admin_manage` 处理“系统主数据和报表”。两者不要因为都叫 Admin 而混为同一权限级别。

## 3. 经营管理页 `admin_manage/`

### 3.1 目标

为经营者提供不需要前端构建的基础后台配置页面。

### 3.2 功能区域

1. 菜单编辑：增删改、上下架、批量删除。
2. 分类管理：创建、改名、拖动排序、删除。
3. 文本导入：批量追加菜单。
4. 区域与二维码：批量建立桌/包厢、改名、重置 token、完成标记、结单和删除；Access Code 展示及轮换入口退役。
5. 日结报表：按浏览器本地日期查询活动和历史订单。
6. 员工账号：新增、修改和删除。

### 3.3 重要现实

页面本身没有登录门槛，对应多数管理 API 也没有管理员鉴权。如果把 `/manage` 暴露到公网，这些操作不能被视为安全。

## 4. React Native 员工 App `apps/employee_app/`

### 4.1 技术结构

- React Native 0.85.3；
- React 19.2.3；
- TypeScript 主界面 `App.tsx`；
- Android Kotlin 启动壳；
- iOS Swift 启动壳；
- `react-native-sound-player` 播放提示音。

产品层面只把 Android 作为正式员工端，目标设备为 Samsung 平板并以横屏为第一布局。iOS 工程存在不代表本轮需要设计或验收 iOS。

### 4.2 业务实现

`App.tsx` 复现员工接单核心流程：登录、订单列表、区域列表、开台、状态处理、明细修改、结算模式、顾客结算标记和结单。共享类型包括 `Zone`、`Order`、`OrderItem`、`WriteQueueInfo` 和结算状态。

默认服务器地址在代码中固定为：

```text
https://order.1383karaoke.ca
```

轮询间隔常量为 1000 毫秒。相比 Windows 端，移动 App 当前没有可见的服务地址配置流程。

### 4.3 Android UI 重构与历史功能强制约束

后续员工 Android 重构必须遵守[员工 Android 重构强制约束](00_MANDATORY_CONSTRAINTS.md)：

- 数据库表、字段、索引、迁移、归档事务、数据库文件和现有写入路径全部禁止修改；
- 当前工作采用“桌台/包厢 → 合单/分单 → 顾客/订单 → 菜品”层级；
- 历史订单作为独立二级入口，不得混入首页当前工作集；
- 历史按“包厢 → 结单批次 → 顾客 → 订单 → 菜品”只读展示；
- 必须分页读取到全部历史，不能用 2000 条截断结果冒充完整；
- 历史读取必须经过员工认证，不得直接依赖未鉴权管理接口；
- 单品备注、永久补单标记、单品取消历史和部分送达不得在 v1 中伪造；所有现有员工端功能必须保留，不得借 UI 重构删除。
- 必须详细遵守[Samsung 安卓平板员工端 UI 最终规格](10_SAMSUNG_ANDROID_TABLET_UI_SPEC.md)，不能只做配色调整或把现有双栏界面换皮。
- 员工 Web 和 Windows 交互 UI 不在本轮范围内，不能作为 Android 验收替代；现有 Windows 打印协议必须保持兼容。

### 4.4 原生目录

- `android/`：Gradle 工程、Manifest、Kotlin Application/Activity、图标和声音资源。
- `ios/`：Podfile、Xcode 工程、AppDelegate、Info.plist、图标和隐私清单。
- `index.js`：注册 React Native 根组件。

这些原生文件大部分是 React Native 脚手架；核心业务集中在 `App.tsx`。

## 5. Windows Electron 打印工作端 `windows_employee_app/`（保留打印、停止功能更新）

### 5.1 进程职责

Electron 分为三层：

| 文件 | 作用 |
| --- | --- |
| `main.js` | 创建窗口、保存配置、代理网络、枚举打印机、打印小票 |
| `preload.js` | 通过 `contextBridge` 暴露受限桌面 API |
| `src/renderer.js` | 员工业务 UI、轮询、结算和打印任务循环 |

窗口启用了 `contextIsolation`，关闭渲染进程 Node 集成。渲染层不能任意访问文件系统，只能调用 preload 明确暴露的方法。

### 5.2 网络方式

渲染进程把路径、方法、请求头和请求体交给主进程，主进程使用 Node `http`/`https` 发起请求。服务地址可在 UI 保存到 Electron 用户数据目录中的：

```text
employee-desktop-config.json
```

默认地址同样是 `https://order.1383karaoke.ca`。

### 5.3 打印方式

主进程把小票 JSON 渲染为独立 HTML，创建隐藏窗口并调用 `webContents.print`：

- 静默打印；
- 打印背景；
- 可选择系统打印机；
- 203 DPI；
- 无页边距。

打印成功与否由 Electron 回调决定，再由渲染进程回报服务端打印任务状态。

现场不再把 Windows 当成员工操作端，但继续运行其打印工作端。Samsung Android 提交打印任务后，Windows 在后台领取任务、调用门店打印机并向服务端回报结果。Windows 员工 UI 不再设计或增加业务功能；任何 Android/服务端改动都必须保持现有任务字段和小票 JSON 兼容。

### 5.4 构建目标

Electron 固定在 22.3.27，README 声明目标为 Windows 7/8/8.1。包配置支持 x64 和 ia32 NSIS 安装程序。仓库中存在已构建的 `dist_win7_ia32` 和 `dist_win7_x64` 内容，但构建文件存在不等于目标系统和真实打印机已经验收。

## 6. 单一正式员工客户端策略

员工 Web、React Native 和 Electron 代码仍各自复制了：

- 状态文案；
- 订单排序；
- 是否可编辑判断；
- 结算模式文案；
- 区域会话展示；
- 轮询和错误处理。

服务端仍负责最终业务规则，但产品决策已经明确：员工交互 UI 只在 Samsung Android App 上继续演进。员工 Web 和 Windows 交互界面不要求同步改版；Windows 仅冻结保留打印工作端。Android 功能完成必须以实际 Samsung 平板为准，而涉及小票或打印协议的改动还必须通过现有 Windows 工作端和真实打印机兼容回归。
