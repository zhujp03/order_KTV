# 11 `admin_manage` 经营后台 UI 最终规格 v1

> [!IMPORTANT]
> 本文件只允许重构 `admin_manage/` 的 UI、信息架构、页面层级和交互组织。Access Code 展示与轮换入口退役是唯一删除例外；除此以外不得新增、删除、替换或改变任何现有功能，也不得要求后端、SQL、数据库结构、归档逻辑或二维码体系配合改变。与本文件冲突时，以[UI 重构最高强制约束](00_MANDATORY_CONSTRAINTS.md)为准。

## 1. 产品定位

`admin_manage` 是经营配置后台，不承担员工现场接单。它继续负责：

- 菜单与分类；
- 桌台/包厢和二维码；
- 日结报表；
- 员工账号；
- 现有隐私说明。

本轮只解决当前多模块堆叠长页的结构问题，不建设新的管理员权限体系、经营分析系统或 POS 业务。

## 2. 功能零增删基线

以下当前能力必须全部保留。

### 2.1 菜单和分类

- 新增菜品；
- 编辑名称、价格、分类、描述和上下架；
- 勾选、全选、删除勾选、删除全部；
- 保存菜单；
- 新增、改名、拖动排序和删除分类；
- 批量导入菜单文本；
- 现有成功、失败和未保存提示。

### 2.2 桌台、包厢和二维码

- 按数量批量创建桌台/包厢；
- 显示桌台名称、token 摘要、当前订单数、当前金额和完成时间；
- 二维码预览；
- 复制访问链接；
- 下载 PNG；
- 下载 SVG；
- 标记完成/取消完成；
- 结单清台；
- 改名；
- 重新生成二维码；
- 删除桌台/包厢。

Access Code 展示与轮换入口不得保留；这是产品明确授权的功能退役例外，不属于误删。

### 2.3 日结报表

- 日期选择；
- 当日订单数和金额摘要；
- 订单列表和现有明细；
- 当前活动/历史来源等现有字段。

### 2.4 员工账号

- 新增员工；
- 修改真实姓名和用户名；
- 可选修改密码；
- 删除员工；
- 现有保存和错误反馈。

### 2.5 其他

- 当前隐私/反追踪说明必须保留；
- 当前定时刷新桌台信息的行为必须保留且不能造成页面频闪；
- 所有调用继续使用原有 API、请求字段和响应语义。

## 3. 页面结构

一级导航固定为：

1. `概览`
2. `菜单`
3. `桌台 / 二维码`
4. `报表`
5. `员工`

布局使用固定左侧导航和右侧模块内容。模块内部可以根据任务使用局部双栏，但不得继续把全部模块堆在同一个滚动长页中。

切换模块属于前端显示组织，不改变 URL/API/业务状态。切换回来时应保留合理的筛选、选择和未保存编辑状态；不得因为切换页面丢失尚未提交的菜单修改。

## 4. 概览页

### 4.1 目标

概览只汇总现有接口已经返回的数据，不新增后端指标或经营口径。

### 4.2 允许展示

- 今日下单金额；
- 今日订单数；
- 当前开台桌数；
- 当前可结单桌数；
- 当前有进行中订单的桌数；
- 当前员工数；
- 最近更新时间；
- 前往菜单、桌台、报表和员工模块的快捷入口。

“有进行中订单桌数”使用现有 `activeOrderCount > 0` 派生。不得在本轮改成需要新增后端字段的“有 new 状态订单桌数”。

### 4.3 金额语义

现有按日报表按订单创建日期统计，因此必须写“今日下单金额”，不能写“今日营业收入”或“今日结单收入”。概览不创造新的财务口径。

### 4.4 隐私说明

现有隐私/反追踪说明放在概览底部的“系统说明”折叠区，内容保留，不单独占据一级导航。

## 5. 菜单页

推荐模块内双栏：

- 左侧：分类列表、新增分类、改名、排序和删除；
- 右侧：菜品表格、新增、批量导入、勾选删除、全部删除和保存。

要求：

- 明确显示“有未保存修改/已保存/保存失败”；
- 删除勾选、删除全部和删除分类继续使用现有确认流程；
- 批量导入是现有功能，不能降级为隐藏且难以发现的入口；
- 上下架、分类选择、描述等现有字段全部保留；
- 不改变覆盖式保存的现有语义。

## 6. 桌台 / 二维码页

### 6.1 布局

- 左侧：桌台列表、当前摘要、选择状态和批量创建入口；
- 右侧：选中桌台详情、二维码预览、链接、统计和操作。

### 6.2 列表摘要

列表只显示：

- 桌台/包厢名称；
- 开台/完成状态；
- 当前订单数；
- 当前金额；
- 当前合单/分单摘要；
- 是否可结单。

token、完整 URL、二维码下载和危险操作放入详情，不在每张列表卡上全部摊开。

### 6.3 详情必须保留

- token 摘要；
- 二维码预览；
- 完整访问链接；
- 复制链接；
- PNG/SVG 下载；
- 标记完成/取消完成；
- 结单清台；
- 改名。

### 6.4 高危区

重新生成二维码和删除桌台集中到独立高危区。

- 普通改名、开台、结单和完成标记不得改变 `zone.token`；
- 重新生成二维码会改变 token，必须明确提示“已打印旧二维码将永久失效”；
- 删除桌台同样会让旧二维码不可用；
- 两项都必须至少二次确认，不能成为卡片上的高频按钮；
- UI 重构本身不得自动调用重新生成或删除接口。

结单按钮的文案应表达“归档并清台”，不能让管理员误解为未保存历史的物理删除；实际行为仍完全沿用现有接口。

## 7. 报表页

- 只做现有报表查询和展示；
- 日期选择固定在页头；
- 先显示订单数和今日下单金额，再显示订单列表；
- 订单明细按现有返回字段展示；
- 不新增导出、对账、利润、支付或结单收入能力；
- 不把报表操作与桌台危险操作混排。

## 8. 员工页

- 列表显示真实姓名和用户名；
- 新增员工使用独立表单或抽屉；
- 编辑继续支持姓名、用户名和可选新密码；
- 删除使用明显危险确认；
- 不新增角色、权限、停用、审计或排班能力；
- 不改变现有账号 API 和密码语义。

## 9. 视觉和交互

- 使用明确文字和高对比状态，不依赖只有图标的按钮；
- 列表看状态，详情做操作；
- 高频动作固定位置，危险动作统一红色和确认流程；
- 页面切换不重置正在编辑的内容；
- 加载、保存、失败、空状态和最近更新时间必须可见；
- 桌台定时刷新不得覆盖管理员正在输入的内容；
- 桌面浏览器为主要使用环境，但仍应适配常见笔记本宽度。

## 10. 后端和数据库边界

- 不增加或修改任何 `admin_manage` 专用 API；
- 不修改现有请求字段、响应字段和调用顺序的业务含义；
- 不修改 SQL、数据库函数、表、字段、索引、迁移、归档或写入语义；
- 系统正常使用原有 API 读写菜单、桌台、员工和订单数据不属于“修改数据库实现”；
- 不直接编辑、替换、清理或重新生成真实数据库文件；
- 不以概览卡片为理由新增统计接口。

## 11. 验收标准

- 进入 `/manage` 默认显示概览；
- 五个模块导航清晰，不再依赖整页向下滚动寻找功能；
- 第 2 节列出的全部现有能力逐项可发现、可操作且结果与重构前一致；
- 菜单未保存状态不会因导航切换丢失；
- 桌台 token 不会因普通操作改变；
- 重置二维码和删除桌台有明确永久失效警告；
- Access Code 不再显示、输入或提供轮换操作；完成标记、PNG/SVG 下载和隐私说明没有被极简化误删；
- 报表金额明确为现有下单口径；
- 没有新增后端路由、SQL或数据库改动；
- 使用真实现有 API 完成菜单、分类、桌台、报表和员工全流程回归。

## 12. 禁止完成声明

以下情况不能声称 `admin_manage` UI 重构完成：

- 只做静态页面或 Mock；
- 任一现有按钮、字段或操作入口消失；
- 为概览新增后端指标或数据库查询；
- 只验证页面能打开，没有执行原有 CRUD；
- 普通桌台操作导致二维码 token 改变；
- 用新的业务语义替换现有接口行为；
- 未检查未保存菜单状态、定时刷新和危险确认。
