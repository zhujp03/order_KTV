# 10 Samsung 安卓平板员工端 UI 最终规格 v1

> [!IMPORTANT]
> 本文件是由 Codex 主控确认的员工端 UI 实施规格。它详细吸收了顾问方案中合理的“桌台优先、姓名次之、订单再次之、菜品最末”“当前工作集”“固定高频操作”和“状态颜色只传达业务”的原则，但所有内容均以当前项目真实能力和[强制约束](00_MANDATORY_CONSTRAINTS.md)为边界。

> [!NOTE]
> 本文件只重新组织当前 Android 功能，但有两个明确例外：新增只读历史回看；删除已废弃的 Access Code 展示和使用。除此以外不增加或删除功能。

## 1. 产品定位

### 1.1 唯一正式员工客户端

- 正式员工工作端只有 `apps/employee_app/` 的 Android App。
- 目标设备是 Samsung 安卓平板。
- 员工 Web 看板 `front_admin/` 不属于日常现场流程。Windows Electron 不再作为员工交互端更新，但继续作为后台小票打印工作端；两者都不作为本次 Android UI 的设计参照或交互验收对象。
- 顾客扫码网页和经营管理网页不受“员工端只使用 Android”约束，它们属于其他角色。
- Android 员工 App 必须独立完成开台、接单、改单、送达、合单/分单、结算标记、结单和历史回看；员工不需要在 Web 或 Windows 界面操作。打印是唯一允许的后台协作例外：Android 发送任务，Windows 工作端自动打印。

### 1.2 设备方向

- Samsung 平板横屏是第一设计方向。
- 不针对某一个固定像素尺寸写死布局；应适配常见 Samsung 平板的宽度、密度和系统字体缩放。
- 竖屏可以提供基本可用的降级布局，但不是 v1 主要验收方向。
- 最终视觉验收必须在实际目标 Samsung 平板完成；只有模拟器截图不能代替最终设备验收。

### 1.3 现场属性

这是员工现场工作台，不是消费级内容 App：

- 信息优先于装饰；
- 文字优先于难以理解的图标；
- 状态优先于品牌视觉；
- 一次触摸完成高频动作；
- 戴手套、站立、忙碌、屏幕有反光时仍应可读可点；
- 不要求员工理解数据库、session、token、队列或 API 等系统概念。

## 2. 业务目标

员工打开 App 后应在 3 秒内知道：

1. 哪个包厢有新单；
2. 哪个包厢正在制作；
3. 哪个包厢有菜待上；
4. 哪个包厢可以结单；
5. 哪个包厢使用合单，哪个使用分单；
6. 当前最应该先处理什么。

新员工第一次使用时不应再询问：

- “名字是做什么的？”
- “这桌是整台结还是分开结？”
- “哪些菜已经送了？”
- “新单在哪里？”
- “怎么完成订单？”
- “怎么结单清台？”
- “以前这间包厢点过什么？”

## 3. 核心信息层级

当前工作固定使用：

```text
桌台/包厢
└── 合单或分单
    └── 顾客/订单
        └── 菜品与送达状态
```

历史回看固定使用：

```text
历史订单
└── 包厢
    └── 结单批次
        └── 顾客
            └── 订单
                └── 菜品快照
```

禁止把桌台、顾客姓名、订单、菜品、结算和历史平铺在同一视觉层级。

## 4. 全局导航

登录后只保留两个一级工作入口：

1. `当前桌台`
2. `历史订单`

导航要求：

- `当前桌台` 永远是默认首页。
- `历史订单` 是明确但次要的只读入口。
- 菜单管理、员工管理、二维码管理、统计报表和系统配置不得进入员工 App 主导航。现有员工 App 功能一个都不能删除；次要能力可以收进详情或次级菜单。
- 当前桌台页面继续实时轮询；进入历史页后不得让历史数据加入高频实时轮询。
- 从历史返回当前桌台时，应恢复原先选中的包厢和滚动位置，不强迫员工重新导航。
- 当前员工、网络状态、最后更新时间和退出登录放在固定顶栏，不占用订单主区域。
- 当前已有的写队列状态不得删除，但它是运维状态而不是员工主任务，应放入固定顶栏的次级系统状态区域并使用员工能理解的文案。

## 5. 登录页

登录页只显示：

- 员工端标题；
- 用户名；
- 密码；
- 登录按钮；
- 中英文切换；
- 登录错误或服务不可用提示。

要求：

- 不显示服务端 URL、HTTP 状态、session token 或调试信息。
- 登录按钮高度至少 56dp。
- 输入框和按钮适配 Samsung 平板软键盘，不被键盘遮挡。
- 登录失败保留用户名但清空密码。
- 登录成功直接进入桌台总览，不先进入全量订单流。

## 6. 页面一：桌台总览

### 6.1 页面唯一目的

桌台总览只回答一个问题：现在哪个包厢需要员工处理？

首页不展示菜品明细、顾客分组详情、完整历史订单或管理信息。

### 6.2 桌台卡片固定内容

每张桌台卡只显示：

- 包厢名称；
- 已开台/未开台；
- 新单数量；
- 制作中订单数量；
- 待上菜订单数量；
- 未送菜品“份数 + 项数”；
- 当前金额；
- 合单/分单；
- 分单时的未结顾客数量，或“可结单”；
- 明确状态文案。

整张卡片可以点击进入详情，不再增加重复的“进入”小按钮。

### 6.3 未送数量定义

```text
未送份数 = 所有 served !== true 菜品的 quantity 总和
未送项数 = 所有 served !== true 菜品明细行数量
```

推荐显示：

```text
未送 5 份 · 3 项
```

当前模型只支持整条菜品明细已送/未送，不能显示“3 份中送了 1 份”。

### 6.4 桌台排序

默认按紧急程度排序，不按创建时间或桌号机械排序：

1. 有 `new` 新单；
2. 有 `ready` 且存在未送菜品；
3. 有 `preparing` 订单；
4. 可以结单；
5. 已开台但暂时无待处理工作；
6. 未开台。

同一优先级内部，较早到达的订单优先。

未开台桌台可以放入“未开台”折叠区域，但不能完全消失，因为员工仍需要从这里开台。

### 6.5 卡片视觉

- 红色：存在新单，必须配“新单”文字和数量。
- 黄色/橙色：制作中或待上菜，必须配具体阶段文字。
- 绿色：当前工作完成或可结单。
- 灰色：未开台或无当前任务。
- 颜色不能成为唯一信息；必须同时有文字、数字和必要的形状差异。
- 卡片不使用无业务含义的渐变、插画或装饰图标。

### 6.6 开台操作

- 未开台卡片的唯一主操作为“开台”。
- 开台必须有明确确认文案，说明会开始新的当前会话。
- 已开台卡片不能继续显示“开台”。
- 开台必须继续使用现有后端能力和业务语义，不增加新的开台模型。
- 当前源码虽然仍显示 Access Code，但它已经被产品废弃。本次必须移除该显示，不得在桌台卡、详情、弹窗或系统状态中以任何形式保留；不得因此修改数据库或后端兼容代码。

### 6.7 Access Code 退役

- Android 不显示 Access Code，不提供查看、复制、输入、校验或轮换入口。
- Android 不向任何请求发送 `accessCode`。
- 开台仍使用现有开台接口；顾客点单资格由桌台开台状态和既有 session 规则决定。
- 现有 TypeScript 数据类型即使暂时仍接收后端兼容字段，也不得把该字段绑定到 UI 或业务判断；是否清理类型必须以不改变 API 和后端为前提。

## 7. 页面二：桌台当前会话工作台

### 7.1 顶部固定区域

进入包厢后，顶部固定显示：

- 返回桌台总览；
- 包厢名称；
- 已开台/未开台；
- 合单/分单；
- 当前总金额；
- 未送份数/项数；
- 是否可以结单；
- 分单时的未结顾客数量；
- 最后刷新时间。

滚动订单时顶部信息不能消失。

### 7.2 当前会话内部层级

桌台详情分为：

- `待处理`
- `当前会话已结束`

`待处理` 默认打开，包含 `new`、`preparing`、`ready`。

`当前会话已结束` 默认折叠，包含尚未结单归档的 `served`、`cancelled`。它不是历史订单页。

### 7.3 合单模式

合单模式以整台处理为主：

- 默认按订单状态流展示；
- 顾客姓名保留在订单卡上，但不成为一级分组；
- 推荐顺序为新单、制作中、待上菜；
- 每个状态内保持先来先处理；
- 结单以整个包厢为单位；
- 不要求员工逐个顾客标记已结。

### 7.4 分单模式

分单模式自动按顾客姓名分组：

- 姓名是一级卡片标题；
- 显示该顾客应付金额；
- 显示订单数量；
- 显示未送份数/项数；
- 显示已结/未结；
- 展开后显示该顾客的全部当前会话订单；
- 未结顾客优先于已结顾客；
- 已结顾客默认可折叠，但其未送菜品仍必须醒目提示，不能因已结而隐藏服务任务。

这里使用“应付金额”而不是含糊的“小计”，因为现有订单总额包含服务费和税。

### 7.5 合单/分单切换

- 切换入口固定在桌台顶部，不放进每张订单卡。
- 当前模式必须以完整文字显示，不只使用图标。
- 切换前显示确认文案，说明页面会改变为整台或按姓名结算视图。
- 切换只调用现有结算模式能力，不创建新的账单模型。

## 8. 订单卡规格

每张订单卡固定显示：

- 顾客姓名；
- 订单状态；
- 下单时间；
- 菜品总份数；
- 未送份数/项数；
- 订单总金额；
- 订单备注；
- 订单状态处理员工。

订单编号可以作为次级信息缩短显示，不得比顾客、状态和时间更醒目。

### 8.1 订单状态主操作

| 当前状态 | 主按钮 | 目标状态 |
| --- | --- | --- |
| `new` | 接单 | `preparing` |
| `preparing` | 制作完成 | `ready` |
| `ready` | 整单完成 | `served` |

要求：

- 每张卡只突出当前唯一主操作，不同时放三个同等权重的状态按钮。
- 当前 App 已支持直接选择多个订单状态。为满足“功能零减少”，其他现有状态修改动作必须保留在次级“更改状态”菜单中；只改变视觉权重，不删除能力或改变后端允许的状态语义。
- “整单完成”与单品“已送”必须区分。
- 取消订单放在次级危险操作中，不与主操作并列。
- 取消必须二次确认，并明确说明订单金额会按现有后端规则处理。

## 9. 菜品明细规格

每条菜品至少显示：

- 菜名；
- 数量；
- 单价或小计；
- 已送/未送；
- 数量调整；
- 是否允许编辑。

### 9.1 单品送达

- 未送：清晰的“标记已送”按钮。
- 已送：绿色勾选和“已送”文字，可在订单仍允许编辑时恢复为未送。
- 已送菜品的数量调整按钮必须禁用。
- 不得显示不存在的部分送达进度。

### 9.2 加菜和数量调整

- “加菜”是订单级操作，固定在订单卡操作区。
- 菜品选择使用大行高列表，显示名称、分类、价格和描述。
- `+`、`-` 只调整现有后端允许的数量。
- 当数量减少会移除菜品时，需要确认或清晰提示。
- 整单至少保留一个菜品的现有规则不能被 UI 绕过。

### 9.3 v1 不展示的内容

- 单品独立备注；
- 永久“新加菜/补单”标记；
- 单品取消/退菜历史；
- 单个数量部分已送；
- 数据模型中不存在的厨房状态。

订单级备注仍然显示在订单卡中。

## 10. 固定操作区

### 10.1 订单操作区

固定顺序：

1. 当前状态的唯一主操作；
2. 加菜；
3. 次级“更改状态”菜单中的其他现有状态动作；
4. 次级菜单中的取消。

### 10.2 菜品操作区

固定顺序：

1. 已送/未送；
2. 减少数量；
3. 增加数量。

### 10.3 桌台底部操作区

固定显示与当前模式相符的状态和最终动作：

- 分单：显示未结人数；全部满足条件后显示“结单并清台”。
- 合单：显示整台模式；满足现有条件后显示“整台结单并清台”。
- “结账”和“结束会话”不能做成两个虚假的独立动作。
- 结单并清台必须二次确认。

## 11. 历史订单页面

历史功能严格遵守[强制约束](00_MANDATORY_CONSTRAINTS.md)，只读且数据库零改动。

### 11.1 历史列表

顶部提供：

- 返回当前桌台；
- 包厢筛选；
- 日期筛选；
- 顾客姓名搜索；
- 清除筛选；
- 加载/错误状态。

每个结单批次卡片显示：

- 包厢历史名称；
- 结单时间；
- 顾客数量；
- 订单数量；
- 菜品数量；
- 总金额；
- 相关员工。

列表按结单时间从新到旧，使用分页和虚拟列表，直至明确显示“已经加载全部历史”。

分页必须遵守[API 强制契约](04_API_REFERENCE.md#12-员工-android-历史接口强制边界目标约束)：筛选条件变化后重新从第一页加载；追加页按批次键和订单 ID 去重；只有服务端返回 `hasMore=false` 才显示加载完成。

### 11.2 历史详情

按顾客分组展开订单和菜品快照，显示当前已有的全部历史字段。所有按钮和控件均为查看性质。

历史详情不得出现：

- 改状态；
- 加菜；
- 改数量；
- 改已送；
- 改结算；
- 结单；
- 删除；
- 管理入口。

无 `checkoutAt` 的记录明确标记“旧版历史记录”，不伪造会话分组。

## 12. 打印能力边界

- 小票打印功能继续保留在现有 Windows Electron 工作端。
- Windows 不再继续开发员工接单、改单、结算或其他交互功能；只冻结保留打印机配置、任务领取、小票渲染、打印和结果回报。
- Samsung Android 可以保留当前会话的小票打印入口，操作含义是“发送打印任务”。
- Android 收到任务入队成功后只能提示“打印任务已发送”，不能提示“打印成功”；最终打印结果由 Windows 工作端和真实打印机决定。
- 员工不需要在 Windows 界面重复接单或确认打印；Windows 应作为后台打印工作站持续运行。
- Android、服务端和小票字段的后续改动必须向后兼容现有 Windows worker，不得要求同步升级 Windows 才能继续打印，除非用户以后单独授权。
- 历史页面 v1 仍保持只读，不默认增加历史小票重打，因为现有打印生成逻辑面向当前包厢会话。
- 涉及打印任务、小票 JSON 或相关 API 的发布，必须使用现有 Windows 工作端和真实门店打印机验证任务领取、成功、失败和连续打印。

## 13. 视觉和触摸规范

### 13.1 尺寸基线

- 普通触摸目标不小于 48 × 48dp。
- 高频主按钮高度不小于 56dp。
- 相邻危险操作之间保留足够间距，防止误触。
- 正文建议不小于 16sp；状态和操作文字建议不小于 18sp；页面标题建议 24sp 或以上。
- 支持系统字体放大，不允许文字覆盖按钮或被硬裁剪。

### 13.2 视觉语言

- 深浅背景均可，但必须满足高对比。
- 少图标，多明确文字。
- 图标出现时必须配文字标签。
- 不依赖 hover、右键或精细鼠标定位。
- 不使用装饰性动画阻断操作。
- 状态切换动画应短且不影响连续接单。
- 危险按钮保持一致的红色和确认流程。

### 13.3 Samsung 平板适配

- 使用可伸缩列数，不按固定 340px 侧栏写死整个工作流。
- 处理状态栏、导航栏、显示挖孔和安全区域。
- 验证 Samsung 系统字体缩放、显示缩放和横屏旋转。
- 长列表滚动时固定顶栏和关键操作区不能抖动。
- 软键盘弹出时，搜索、登录和备注输入仍可见。

## 14. 加载、错误和反馈

- 首次加载显示骨架或明确加载状态，不显示空白页。
- 后台轮询不得每秒闪烁整个页面或重置滚动位置。
- 写操作进行中只锁定相关按钮，不无差别锁死全部工作台。
- 成功操作使用短反馈，不用连续弹窗打断员工。
- 网络中断显示顶部持续状态，并允许手动重试。
- session 过期清理敏感状态并返回登录页。
- 空桌台、无订单、无历史、筛选无结果和历史加载完成必须使用不同文案。

## 15. 隐藏和禁止展示的信息

员工日常 UI 不显示：

- 数据库、表名、字段名；
- HTTP 状态码和接口路径；
- session token、二维码 token、内部 UUID；
- 写队列内部 ticket；
- 堆栈和原始异常；
- 菜单管理、员工管理、二维码管理、报表和系统配置；
- Web/Windows 客户端入口或切换提示。

技术错误应转换成员工能行动的语言，例如“网络连接失败，请重试”，而不是“HTTP 500”。

## 17. 完成标准

只有同时满足以下条件才能声明 Samsung 安卓员工端 v1 完成：

- 日常员工交互不依赖员工 Web 或 Windows 界面；Windows 只在后台承担固定打印职责；
- 桌台总览能在 3 秒内表达紧急任务；
- 合单/分单自动使用正确信息层级；
- 订单状态和单品送达状态不会混淆；
- 当前工作和历史彻底分离；
- 每一条归档历史可通过只读分页访问；
- 数据库改动为 0；
- Android 自动化和静态检查结果如实记录；
- 在实际目标 Samsung 平板完成运行、截图和视觉验收；
- 现有 Windows 打印链路保持可用，Android 入队成功没有被错误表述为已经打印成功。
