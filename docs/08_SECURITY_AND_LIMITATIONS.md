# 08 安全、限制与上线前事项

## 1. 结论

当前代码有基础安全意识：随机 token、顾客/员工会话、服务端重算价格、CSP、安全响应头、SQLite 事务和 Electron 上下文隔离都已实现。但它还不能直接作为安全的公网经营后台上线，最关键原因是管理接口鉴权缺失和默认凭证/密码方案过弱。

## 2. P0：上线前必须处理

### 2.1 管理页面和多数管理 API 无鉴权

任何能访问服务器的人都可能调用菜单、分类、区域、二维码、员工、历史和报表接口，包括：

- 创建/删除员工；
- 修改菜单价格；
- 读取响应中遗留的 Access Code 兼容字段或调用遗留轮换接口；
- 删除区域；
- 触发管理结单；
- 查看历史与日结数据。

应建立独立管理员认证和角色授权，并在服务端保护每一条管理路由。仅隐藏 `/manage` 链接、使用难猜 URL 或依赖防火墙都不是完整授权模型。

### 2.2 默认员工账号和弱密码哈希

空数据库会创建固定默认账号，并把明文初始口令写到控制台。密码使用无盐 SHA-256，容易遭受离线字典攻击。

建议：

- 不再自动创建固定账号；首次启动使用一次性初始化流程；
- 使用 Argon2id、scrypt 或 bcrypt 等专用密码哈希；
- 增加密码强度、失败锁定和强制改密；
- 不在日志输出凭证。

### 2.3 Access Code 退役后的访问边界

当前产品明确废弃 Access Code，点单依赖“员工开台 + 顾客短期 session”，目标部署必须关闭 Access Code 校验和轮换。二维码链接仍是长期标识，因此开台时间控制、session 撤销、管理入口保护和异常点单监控更重要。恢复 Access Code 不是本次 UI 重构允许的补救方式。

### 2.4 数据库与管理入口保护

SQLite 包含员工哈希、session token、订单、姓名和经营数据。需要：

- 限制文件权限；
- 加密备份；
- 不把数据库、WAL 或备份放到静态目录；
- 管理入口使用 HTTPS 和网络/身份双重保护；
- 对破坏性管理操作增加确认、授权和审计。

## 3. P1：高优先级加固

### 3.1 缺少限速和防爆破

登录和 session 打开接口没有服务端限速。即使 Access Code 已退役，也应按账号、区域、IP 和时间窗口限速，并在连续失败时增加冷却；遗留 Access Code 路由若仍可达，同样属于需要保护的兼容攻击面。

### 3.2 没有管理员/员工角色细分

员工登录后可使用所有员工 API；管理 API又多数完全开放。应定义最小权限，例如服务员、收银、经理、系统管理员，并明确每条 API 的权限矩阵。

### 3.3 状态流转未由后端强制

状态接口允许在任意允许值之间跳转，也可能把取消订单再改成其他状态。应建立明确状态机、冲突检测和审计记录。

### 3.4 没有并发版本控制

写队列能串行化单进程写入，但没有订单版本号或 `updated_at` 条件更新。多个员工几乎同时操作时，后请求可能覆盖前请求意图。需要乐观锁或明确冲突响应。

### 3.5 session 保存在浏览器 localStorage

顾客和员工 Web token 可被同源 XSS 读取。当前 CSP 禁止外部/内联脚本，降低了风险，但仍应保持输出转义、避免引入不可信脚本，并考虑更安全的 HttpOnly Cookie 会话设计。

### 3.6 错误响应暴露内部消息

全局 500 响应包含异常 `detail`。生产环境应返回稳定公共错误码，把详细堆栈只写到受保护日志。

### 3.7 缺少审计日志

修改价格、删除区域、调用遗留 Access Code 轮换接口、改员工、改单、结账和结单都应记录操作人、前后值、时间和请求来源。当前只有订单的最后处理员工快照，不能构成完整审计。

### 3.8 修改员工密码不会撤销旧 session

员工更新接口会写入新用户名或密码，但不会撤销该员工已经签发的 session。密码泄露后的改密不能让旧 token 立即失效，应在敏感账号变化后撤销全部旧 session。

## 4. 已实现的防护

- 随机二维码 token、顾客 session 和员工 session 使用 `crypto` 生成；
- 顾客 session 与区域绑定，并可过期/撤销；
- 服务端验证开台状态；
- 服务端根据菜单重算价格和可用状态；
- 文本输入做长度限制和裁剪；
- 数据库启用外键和事务；
- 写请求有队列上限，积压时返回 503；
- 响应包含 `nosniff`、`SAMEORIGIN`、`no-referrer`、Permissions Policy 和 CSP；
- API 响应使用 `Cache-Control: no-store`；
- Electron 启用 `contextIsolation` 并关闭 `nodeIntegration`；
- Electron 只通过 preload 暴露有限能力。

这些防护是基础，不抵消缺失鉴权的问题。

## 5. 隐私边界

管理页声明默认不接第三方统计、字体脚本或设备指纹；当前静态页面也确实主要使用本地资源。但代码仍会保存：

- 顾客姓名；
- 订单内容和时间；
- 员工账号与处理记录；
- 顾客和员工 session；
- 打印内容。

`privacy_mode` 当前主要是设置值，没有形成完整的数据保留/删除策略。正式使用需要隐私告知、最小保留期限、访问控制和删除流程。

## 6. 性能与扩展限制

- 单 Node 进程、单 SQLite 文件；
- 所有 API 写请求完全串行；
- 多客户端以 1 秒级轮询为主；
- 订单和历史读取存在全量读取后在 JavaScript 过滤的路径；
- 日结把活动与历史全部载入后过滤；
- 打印任务没有超时回收和清理。

对单店低并发可能足够，但没有容量测试数据，不能给出可承载人数或 QPS 承诺。

## 7. 业务与数据限制

- 税率、服务费率和小票场所默认值写在代码中；
- 区域没有明确类型字段；
- 分类靠名称与菜单关联；
- 货币存为 SQLite REAL；
- 取消订单会把金额归零，历史无法直接看到取消前金额；
- 没有支付状态，`settled` 是员工手工标记；
- 没有退款、折扣、服务费豁免或税务例外；
- 没有打印任务自动重试；
- 日结依赖客户端传入时区偏移。
