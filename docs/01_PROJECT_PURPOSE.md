# 01 项目含义、目标与边界

## 1. 一句话定义

Order System 是一套把“桌台/包厢二维码、顾客自助点单、员工接单处理、分客结算和本地小票打印”连接在一起的单店订单系统。

## 2. 它解决什么业务问题

传统包厢服务依赖顾客呼叫员工、员工手写或口头传单，再由前台和后厨重复确认。这个项目试图把这一链路数字化：

1. 经营者为每个桌台或包厢建立一个长期二维码。
2. 员工在顾客到店后开台。
3. 顾客扫码并输入姓名，建立属于自己的短期会话；员工未开台时不能点单。
4. 同一包厢的不同顾客分别维护购物车并下单。
5. 员工在接单端看到实时订单，处理状态、加菜、改单和送达标记。
6. 结账时选择分开结账或整房合并，生成并打印小票。
7. 结单后订单进入历史记录，活动区被清空，旧会话失效。

核心价值不是“做一个菜单页面”，而是建立一条可追踪的包厢服务闭环。

## 3. 主要使用角色

| 角色 | 使用入口 | 主要目标 |
| --- | --- | --- |
| 顾客 | 手机浏览器扫码页 | 查看菜单、维护个人购物车、提交订单、查看本包厢订单 |
| 服务员工 | Samsung 安卓平板上的 React Native App | 开台、接单、改单、标记送达、合单/分单、结账、结单和历史回看 |
| 小票打印工作站 | Windows Electron 固定打印工作端 | 不再更新员工交互功能，只保留领取打印任务和驱动门店打印机的能力 |
| 经营者/管理员 | 管理页面 | 管理菜单、分类、桌台二维码、员工账号和日结数据 |
| 运维人员 | 服务器和环境配置 | 维护域名、数据库、反向代理、备份和进程运行 |

## 4. 产品设计目标

### 4.1 以开台和短期会话控制点单

二维码 URL 中的 token 用于定位包厢，但正常点单还需要：

- 员工已把包厢置为“开台”；
- 顾客提供姓名；
- 服务端签发的 `X-Zone-Session` 会话仍然有效。

结单后旧会话会被撤销。Access Code 已从产品流程退役：目标前端不得显示、输入或发送它，目标部署必须通过现有配置关闭校验和结单轮换。数据库兼容字段和后端兼容代码保留，本次不做物理清理。

### 4.2 支持多人同房、个人归属

每个顾客会话有独立购物车，订单记录顾客姓名。员工端可以按顾客查看本次包厢会话中的订单，并逐个标记是否完成结算。

### 4.3 以 Samsung 安卓平板为唯一员工工作端

员工现场只使用 Android App，目标设备是 Samsung 平板。员工 Web 不投入现场使用；Windows Electron 不再作为员工操作端更新，但继续在后台承担小票打印。员工业务规则仍以服务端为准，Android 负责唯一正式交互工作台，Windows 只负责固定打印职责。

### 4.4 保留本地打印能力

云端 Node 服务通常不能直接控制门店 USB/局域网打印机。系统继续由 Samsung Android 员工端提交打印请求，服务端保存打印任务，现有 Windows Electron 工作端在后台领取任务并驱动门店打印机。Windows 员工交互 UI 不再继续更新，但这条打印链路必须保留；Android 端只在任务成功入队时提示“打印任务已发送”，不能误报“打印成功”。

### 4.5 轻量、低依赖、易部署

根项目只依赖 Express、better-sqlite3 和 qrcode。没有 Redis、消息队列或独立前端构建流程，便于单店快速部署和维护。

## 5. 明确不属于当前项目的能力

当前代码没有实现或无法从仓库证明以下能力：

- 在线支付、银行卡收单、退款或支付对账；
- 库存、采购、供应商和成本核算；
- 后厨 KDS 专用界面或厨房打印路由；
- 预约、会员、优惠券、积分或营销自动化；
- 多门店、租户隔离、门店级权限；
- 精细角色权限、审计日志和管理员登录体系；
- 云端高可用、自动扩缩容和跨实例写入协调；
- 已验证的数据备份/恢复、灾难恢复或容量指标；
- 真实打印机、真实 Windows 7、Android/iOS 实机验收；
- PCI、隐私法规、税务或无障碍合规认证。

因此，更准确的定位是“单店扫码点单与员工处理系统的可运行实现”，而不是已完成商业验收的全功能 POS 平台。

## 6. 成功标准

如果以当前业务目标判断，最小成功闭环应满足：

1. 管理员能够建立菜单和包厢二维码。
2. 员工能够登录并开台。
3. 顾客只能在有效包厢会话中下单。
4. 后端重新计算价格，不信任顾客提交的价格。
5. 员工能看到新单并完成状态处理、加菜和数量调整。
6. 分开结账时未结顾客会阻止结单。
7. 小票能在真实门店打印机正确输出。
8. 结单后活动订单进入历史，旧顾客会话不能继续下单。
9. 管理接口受到可靠鉴权保护，默认口令已被移除。
10. 数据库有经过恢复演练的备份方案。

目前 1 至 6 的主要代码路径存在；7 至 10 仍需要补强或外部验证。
