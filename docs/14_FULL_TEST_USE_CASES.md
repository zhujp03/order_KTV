# order_system 全量测试用例

> 用途：本文件是本次 UI 重构与现有业务功能的验收测试清单。测试人员应逐项记录实际结果，**不得因页面存在或接口返回 200 就判定通过**。
>
> 覆盖范围：Samsung Android 平板员工 App、顾客扫码点单页、`admin_manage`、服务端现有业务链路，以及 Windows 后台打印工作端的兼容性。

---

## 1. 测试边界与判定规则

### 1.1 必须遵守的边界

- 不直接编辑 SQLite、WAL、SHM、JSON 数据文件；不执行迁移或手工 SQL。
- 所有创建、修改、开台、结单、删除都只通过现有正式 UI 或 API 完成。
- 不修改任何二维码 token、Access Code 相关环境变量、数据库结构或归档逻辑来“让测试通过”。
- Access Code 已退役：员工 App、顾客点单页和 `admin_manage` 均不应展示、询问、校验或调用其轮换接口。
- Android 的打印反馈只能是“打印任务已发送”；真实打印结果必须由 Windows 打印工作端和打印机验证。
- 历史订单页必须只读；不得以当前会话中的 `served`/`cancelled` 订单冒充已归档历史。

### 1.3 测试数据建议

创建专用测试包厢，例如 `TEST-A-合单`、`TEST-B-分单`、`TEST-C-历史`，并准备：

- 至少 3 个上架菜品，价格不同；1 个下架菜品；至少 2 个分类；
- 两名测试顾客（如“测试甲”“测试乙”）和两名测试员工；
- 至少一张 `new`、`preparing`、`ready`、`served`、`cancelled` 订单；
- 至少一批合单历史和一批分单历史；
- 一台已关闭包厢和一张已打印的旧二维码，专门用于二维码稳定性回归。

### 1.4 结果标记与证据

- `[ ] PASS`：实际结果完全符合预期，附截图、录屏、接口响应或打印件。
- `[ ] FAIL`：记录复现步骤、实际结果、时间、设备与截图。
- `[ ] BLOCKED`：测试环境/设备/权限缺失，不可写成通过。
- `[ ] N/A`：仅在功能确实不适用于该环境时使用，并说明理由。

每条 P0 失败都阻断上线；P1 失败需明确风险与修复计划；P2 可列入后续迭代。

## 2. 测试总路径

```text
管理员准备菜单/包厢 → 员工登录并开台 → 顾客扫码点单
→ 员工接单、送菜、加菜、结算、打印 → 结单清台并归档
→ Android 历史只读回看 + admin_manage 报表核对
```

关键一致性要求：同一笔订单在顾客端、Android 员工端、管理报表和历史归档中的名称、数量、金额、状态及包厢归属不得互相矛盾（允许各端展示层级不同）。

## 8. Android 历史订单（只读、员工鉴权、连续分页）

| --- | --- | --- | --- |
| HIS-01 | P0 | 未登录直接进入历史，或清空/伪造员工 session 后请求历史。 | 被拒绝并回到登录；历史数据不能通过未鉴权 Android 正式链路读取。 |
| HIS-02 | P0 | 已登录进入“历史订单”。 | 仅显示已结单归档批次；不混入当前会话 `served` 或 `cancelled` 订单。 |

| HIS-04 | P0 | 对包厢、日期、顾客姓名分别筛选，再组合筛选和清除筛选。 | 筛选作用于完整历史后再分页；顾客命中时保留该批次完整顾客/订单；更改筛选会丢弃旧 cursor 与旧结果。 |
| HIS-05 | P1 | 使用无结果筛选、非法日期、网络失败后重试、加载到底后重复点击。 | 分别显示“无历史/无结果/失败可重试/已加载全部”；不重复请求或重复渲染。 |
| HIS-06 | P0 | 打开合单与分单历史详情。 | 显示包厢快照、结单时间、顾客/订单/菜品数量、总金额、相关处理员工；展开后显示顾客、订单号、下单时间、最终状态、备注、菜名、单价、数量、小计、已送快照、归档/结单时间。 |
| HIS-07 | P0 | 在历史详情中寻找并尝试改状态、加菜、改数量、改已送、结算、结单、删除。 | 所有写操作均不存在且不可通过隐藏入口触发。 |

| ID | 优先级 | 检查 | 预期结果 |

## 16. 建议自动化检查与人工设备验收的分工

### 16.1 可自动化或半自动化

- TypeScript：`cd apps/employee_app && npx tsc --noEmit`
- Android lint：`cd apps/employee_app && npm run lint`
- Android 单元/组件测试：`cd apps/employee_app && npm test -- --runInBand`
- Android 构建：`cd apps/employee_app/android && ./gradlew assembleDebug`
- Release 构建（仅在需要产物时）：`cd apps/employee_app/android && ./gradlew assembleRelease`
- JavaScript 语法：`node --check app.js`、`node --check admin_manage/app.js`、`node --check front_user/app.js`
- API 合约：用专用测试数据覆盖 ENV、API-HIS、CUS、OPS、PRT 中的 P0 路径。

上述命令通过只能证明静态/构建或局部契约；不能替代真实 Samsung 平板触摸、二维码相机扫描、AWS 配置、Windows 打印机和纸质小票验收。

### 16.2 必须人工或真实设备完成

- Samsung 横屏可用性、字体缩放、软键盘、安全区、长列表滚动；
- 真实二维码扫描并在开台/关台前后验证；
- 至少两台顾客设备并发购物车；
- Android 发打印任务 + Windows worker 领取 + 真实打印机出纸；
- 历史超过两页的连续加载、筛选、去重与加载到底；
- 结单归档后的跨端核对。
