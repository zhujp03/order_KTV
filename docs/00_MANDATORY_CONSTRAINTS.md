# 00 UI 重构最高强制约束

> [!IMPORTANT]
> 本文件是 Samsung Android 员工端、`admin_manage/` 经营后台、历史订单只读例外和 Access Code 前端退役例外的最高优先级约束。它不是建议、参考或可选方案。任何实现计划、顾问意见、代码改动和验收结论只要与本文件冲突，都必须以本文件为准并立即停止冲突改动。

## 1. 主控与适用范围

- Codex 是本项目实施和验收主控；外部顾问方案只作为输入，不直接构成实施指令。
- 本约束适用于 `apps/employee_app/` 的员工 Android 平板 UI 重构、`admin_manage/` 经营后台 UI 重构、`front_user/` 的 Access Code 界面退役、历史订单查看功能以及为历史功能提供数据的必要 HTTP 路由层。
- 本轮目标是只重做两个前端的信息架构、页面层级、视觉和交互组织；不得改变现有功能集合、业务语义或后端逻辑。
- 本轮只有两个明确的功能集合例外：Android 新增只读历史回看；Access Code 从 Android、`admin_manage` 和顾客点餐前端中退役。除此以外不得给任何目标前端增加、删除或替换功能。
- 顾问提出的桌台优先、当前工作集、合单/按姓名分单、订单与单品状态分层、固定高频操作和现场工作面板原则，已经由 Codex 审核后纳入[Samsung 安卓平板员工端 UI 最终规格](10_SAMSUNG_ANDROID_TABLET_UI_SPEC.md)，实施时必须详细遵守，不得只做表面配色或局部换皮。

### 1.1 唯一员工端与目标设备

- 正式员工工作端只使用 Android App，目标设备为 Samsung 安卓平板。
- Samsung 平板横屏是第一设计和验收方向，布局不得按单一像素尺寸写死。
- `front_admin/` 员工 Web 看板不投入现场使用，不属于本次开发、设计或验收范围。
- `windows_employee_app/` 不再作为员工交互工作台继续更新，但必须保留并继续承担现有小票打印工作端职责。
- 不得为了保持多端 UI 一致而扩大改动到员工 Web 或 Windows 交互界面。
- Android 日常工作流不得要求员工在 Windows 上接单、改单、结算或操作界面；Windows 只允许在后台领取打印任务并驱动打印机。
- Android 可以继续提交现有打印任务，但提示必须写成“打印任务已发送”，不得在只有入队成功时显示“打印成功”。
- 后续 Android 或服务端改动必须保持现有打印任务、小票 JSON 和 Windows worker 协议兼容；不得以“Windows 不更新”为理由破坏打印功能。
- 顾客扫码网页和经营管理网页属于不同角色，不受“员工端只用 Android”的范围限制。
- 详细页面、触摸、状态、历史和 Samsung 设备规范以[UI 最终规格](10_SAMSUNG_ANDROID_TABLET_UI_SPEC.md)为准。

### 1.2 功能集合冻结

- “只改 UI”是功能冻结，不是允许重新定义业务。
- Android 当前已有的登录、中英文、全桌/桌台查看、开台、结单、订单状态修改、取消、单品已送/恢复未送、数量增减、加菜、合单/分单、顾客结算、当前小票任务发送、新单提示、写队列状态和退出登录等能力必须全部保留；Access Code 展示是本轮明确删除的例外。
- `admin_manage/` 当前已有的菜单增删改、上下架、勾选/全部删除、分类创建/改名/排序/删除、文本导入、桌台批量创建、token/链接/二维码展示、复制、PNG/SVG 下载、完成标记、结单、改名、重置二维码、删除桌台、日结查询、员工增删改和隐私说明必须全部保留；Access Code 展示和轮换入口是本轮明确删除的例外。
- 高频能力可以变成唯一醒目的主按钮；其他现有能力可以进入详情页、次级菜单或高危区，但必须仍然可发现、可操作、调用原有接口并保持原语义。
- 不得用“极简”为理由隐藏到无法发现、禁用、删除或改变任一现有能力。
- Access Code 已被产品废弃：Android、`admin_manage` 和 `front_user` 不得显示、输入、校验、发送或提供轮换入口。顾客是否可以点单只由桌台是否开台和既有顾客 session 规则决定。
- `zones.access_code` 与 `zones.access_code_updated_at` 是现有数据库字段，必须原样保留；不得为退役 Access Code 修改表结构、SQL、迁移、初始化、归档或真实数据库文件。
- 当前后端仍保留条件校验、生成和轮换兼容代码。本轮不得删除或重写这些后端路径；部署必须通过既有配置明确设置 `ZONE_ACCESS_CODE_REQUIRED=false` 和 `ROTATE_ACCESS_CODE_ON_CHECKOUT=false`，使其不参与实际点单流程。
- `front_user/` 除移除 Access Code 输入、提示、请求字段和相关前端分支外不属于本次 UI 重构范围，不得借机重做顾客页面。

## 2. 数据库零改动红线

以下操作全部禁止：

1. 不得新增、删除、重命名或修改任何数据库表、字段、索引、外键、触发器。
2. 不得新增或修改 `CREATE TABLE`、`ALTER TABLE`、`DROP TABLE`、迁移、回填和初始化逻辑。
3. 不得修改现有订单归档表、归档字段或结单归档事务。
4. 不得修改现有数据库写入、结单、清台、历史保存和数据删除语义。
5. 不得直接修改、替换、清理或重新生成 `database/store.sqlite3`、WAL、SHM 或任何真实运行数据。
6. 不得修改 `database/store.json`，也不得重新触发旧 JSON 迁移来满足历史页面。
7. 不得为了历史页面建立新的本地 SQLite、Realm、镜像数据库或持久化历史副本。
8. 不得通过脚本补造、改写或修复历史数据。
9. 不得以“只加一个字段”“只加一个索引”“方便分页”为理由突破本红线。

历史功能只能读取系统已经保存的历史记录。数据库保持现状不动。

## 3. 后端冻结与唯一允许的路由例外

- 除历史只读路由适配外，后端业务函数、现有路由、请求/响应语义、中间件、配置规则和写入路径全部冻结。
- Android 和 `admin_manage` 的 UI 重构必须复用现有 API，不得要求后端增加概览指标、修改状态规则、改变结算、打印、二维码或账号逻辑。
- Android 前端可以增加纯 UI 状态、筛选、排序、分组和内存分页结果，但不得借此创造新的业务状态或持久化能力。
- 如现有历史 HTTP 接口不足，只可以在 HTTP 路由层增加员工认证保护的历史只读适配接口。
- 只读适配接口必须复用现有历史读取能力，不得新增或修改 SQL、数据库函数、表结构和归档逻辑。
- 历史接口必须使用有效的 `X-Employee-Session`；未登录或 session 过期必须返回 `401`。
- Android 员工端不得直接依赖当前未鉴权的 `/api/admin/orders/history` 作为正式实现。
- 历史读取不得触发任何 `POST`、`PUT`、`PATCH`、`DELETE`、结算标记、打印或其他写操作。
- 历史数据只在当前 App 内存中展示；退出登录后清空，不建立新的永久副本。

### 3.1 Access Code 后端兼容边界

- Access Code 退役不授权删除后端路由、函数、响应字段或数据库字段。
- 前端不得调用 `/api/admin/zones/:id/access-code/rotate`，顾客打开 session 时不得提交 `accessCode`。
- 服务端通过现有 `ZONE_ACCESS_CODE_REQUIRED=false` 跳过 Access Code 校验，不得为此新增或修改后端业务逻辑。
- `ROTATE_ACCESS_CODE_ON_CHECKOUT=false` 必须关闭结单轮换，避免继续把已废弃字段当成业务状态。
- 如果未来需要物理删除字段、路由和兼容代码，必须作为单独后端清理任务重新审核，不能并入本次 UI 重构。

## 4. 历史订单功能强制目标

员工 Android 端必须可以重新查看以前已经结单归档的每一个包厢订单详细记录。

历史信息层级固定为：

```text
历史订单
└── 包厢
    └── 一次结单记录
        └── 顾客姓名
            └── 订单
                └── 菜品明细
```

每次结单记录至少显示：

- 包厢名称；
- 结单时间；
- 顾客数量；
- 订单数量；
- 菜品项数与数量；
- 总金额；
- 相关处理员工。

订单详情至少显示：

- 顾客姓名；
- 订单编号；
- 下单时间；
- 订单最终状态；
- 订单备注；
- 菜名、单价、数量、小计；
- 单品已送/未送快照；
- 订单金额；
- 处理员工；
- 归档时间和结单时间。

## 5. 历史分组规则

- 正常历史记录使用 `zoneId + checkoutAt` 作为一次结单批次的客户端分组键。
- 同一次结单产生的订单必须出现在同一结单记录下。
- 包厢改名后，历史页面显示历史记录中保存的 `zoneLabel` 快照，不使用当前包厢名称覆盖旧记录。
- 缺少 `checkoutAt` 的旧版数据不得伪造结单批次；应单独标记为“旧版历史记录”，仍允许展开查看原始订单详情。
- 当前尚未结单的 `served`、`cancelled` 订单仍属于当前会话，不得提前伪装成已归档历史。

## 6. “每一个历史订单”的强制含义

- 不得只加载最新 200 条或最多 2000 条后宣称历史完整。
- 必须使用分页或连续加载，直到服务端明确返回没有下一页。
- 页面需要显示加载状态、失败重试和“已经加载全部历史”的明确状态。
- 筛选不得破坏完整性；清除筛选后必须可以继续查看全部已加载记录。
- 数据量增加后仍应使用虚拟列表或等效机制，禁止一次渲染全部详情导致平板卡顿。

### 6.1 历史分页强制契约

- 正式员工历史接口固定为 `GET /api/employee/orders/history`，必须使用 `X-Employee-Session`。
- 请求支持 `cursor`、`limit`、`zoneId`、`date`、`customerName` 和 `tzOffsetMinutes`；`cursor` 必须是不透明稳定游标，不能用会随新增数据漂移的页码偏移量冒充。
- 响应固定包含 `history`、`nextCursor` 和 `hasMore`；只有 `hasMore === false` 才能显示“已经加载全部历史”。
- 服务端必须先从完整历史集合形成结单批次，再按包厢、日期或顾客条件筛选，然后使用稳定键排序和分页。顾客姓名筛选命中某一批次时，返回该批次完整详情，不能只返回匹配顾客造成批次金额残缺。
- 正常批次按 `checkoutAt` 从新到旧排序，同时间使用稳定 `batchKey` 决胜；无 `checkoutAt` 的旧版记录使用独立 legacy key，不伪造结单时间。
- 分页边界不得拆开同一 `zoneId + checkoutAt` 结单批次。
- Android 每次筛选条件变化都必须清空旧游标和旧结果后从第一页重新请求；追加页按 `batchKey` 和订单 ID 去重，不得产生重复批次或重复订单。
- 无效或与当前筛选不匹配的游标返回稳定 `400`，不得静默回到第一页并制造重复数据。

## 7. 历史页面只读红线

历史页面不得提供：

- 修改订单状态；
- 修改菜品数量；
- 修改已送状态；
- 加菜、退菜或取消；
- 修改顾客已结状态；
- 再次结单或清台；
- 修改归档时间、结单时间或金额；
- 删除历史；
- 通过历史详情调用任何管理操作。

如需要重新打印，只能作为后续独立需求审核；v1 历史页面不默认加入打印按钮。

## 8. 员工端 UI 信息架构强制规则

### 8.1 当前工作与历史必须分离

- 首页只服务当前工作集，不展示大段历史。
- 历史订单作为明确的二级入口，不能抢占新单、待处理和待上菜的主要视觉区域。
- 从历史页返回后，当前桌台选择、实时轮询和工作状态不能丢失。

### 8.2 当前工作层级

```text
桌台/包厢 → 合单/分单 → 顾客/订单 → 菜品
```

- 首页先展示哪个桌台需要处理。
- 合单模式默认按订单工作流展示。
- 分单模式默认按顾客姓名分组展示。
- 订单状态和单品送达状态必须分开表达。

### 8.3 状态定义

- 新单：仅 `new`。
- 当前工作：`new`、`preparing`、`ready`。
- 当前会话已结束订单：`served`、`cancelled`，默认折叠。
- 历史订单：执行结单后已经归档的记录。
- 单品已送/未送：只使用现有 `item.served`，不得推断不存在的部分送达状态。

### 8.4 不允许伪造的能力

现有数据无法可靠支持的以下内容不得进入 v1：

- 单品独立备注；
- 永久“新增/补单”标记；
- 单品退菜/取消历史状态；
- 单个数量的部分送达；
- 把当前会话已完成订单冒充历史归档。

## 9. 交互和危险操作约束

- 高频操作位置必须稳定：接单、制作完成、整单完成、加菜、结单。
- 订单级状态和菜品级已送状态不得共用含糊文案。
- `new` 的主操作为“接单”，对应 `preparing`。
- `preparing` 的主操作为“制作完成”，对应 `ready`。
- `ready` 的主操作为“整单完成”，对应 `served`。
- 上述推荐下一步可以作为唯一醒目的主按钮，但当前 Android 已有的其他状态修改能力必须保留在清晰的次级“更改状态”入口中，不能因视觉简化而删除。
- “已送/未送”只用于单个菜品明细。
- 取消订单、结单并清台等危险操作必须二次确认。
- “结账”和“结束会话”不得伪装成两个独立后端能力；当前最终动作统一表达为“结单并清台”。

## 10. 强制验收标准

### 10.1 数据库保护验收

- `database/` 下不得出现本任务产生的任何改动。
- 数据库建表、迁移、索引、回填、归档事务和现有写入路径不得发生差异。
- 验收报告必须单独列出“数据库改动：0”。
- 只读历史浏览不得改变任何订单、结算、打印或会话数据。

### 10.2 历史完整性验收

- 能按包厢打开不同结单批次。
- 能展开顾客、订单和全部菜品明细。
- 能通过分页加载到服务端明确结束，而不是停在 2000 条。
- 无 `checkoutAt` 的旧数据有明确降级展示。
- 网络失败可以重试，重复分页不会产生重复订单。
- 未登录和过期员工 session 无法读取历史。

### 10.3 Android 验收

- TypeScript 检查和 Lint 无新增错误。
- Jest 配置若仍被既有依赖阻塞，必须如实报告，不能写成测试通过。
- 可以先在 Android 模拟器回归，但最终必须在实际目标 Samsung 平板运行。
- 必须提供桌台首页、合单详情、分单详情、历史列表、历史详情和空/错状态截图。
- 必须进行视觉检查，确认横屏触摸区域、字号、对比度、滚动和返回路径可用。
- 必须记录 Samsung 平板型号、Android 版本、显示缩放、App 构建版本和测试时间。
- 员工 Web 和 Windows 客户端不作为本任务的替代验证，也不要求同步重做 UI。
- Windows 员工交互 UI 不要求验证或更新；如改动涉及小票、打印任务或相关 API，仍必须用现有 Windows 打印工作端和真实打印机做兼容回归。

### 10.4 `admin_manage` 验收

- 必须逐项对照重构前功能清单，证明每一个现有操作仍可发现、可执行且结果语义一致。
- 不得为了概览或导航新增后端路由、字段、SQL或数据库逻辑。
- 当前菜单未保存状态、桌台定时刷新、完成标记、PNG/SVG 下载和隐私说明不得丢失；Access Code 展示和轮换入口必须消失。
- 重置二维码和删除桌台必须明确提示旧二维码永久失效；普通操作不得改变 `zone.token`。
- 详细页面结构和验收以[`admin_manage` UI 最终规格](11_ADMIN_MANAGE_UI_SPEC.md)为准。

## 11. 禁止的完成声明

以下情况不能声称功能完成：

- 只写了 UI 静态页面，没有读取真实历史接口；
- 只展示 Mock/fixture 历史数据；
- 只通过 TypeScript、Lint 或语法检查；
- 只显示最新一部分历史；
- 直接调用未鉴权管理接口；
- 没有 Android 运行和截图验证；
- 只在普通浏览器、员工 Web、Windows 客户端或非目标设备截图验证；
- Android 或服务端改动破坏现有 Windows 小票打印工作端；
- 除只读历史新增和 Access Code 前端退役外，Android 或 `admin_manage` 任一现有功能因“极简”被删除、失去入口或改变语义；
- 除历史只读适配外修改后端路由或业务逻辑；
- 对数据库、归档或历史数据产生了任何未经允许的修改。
