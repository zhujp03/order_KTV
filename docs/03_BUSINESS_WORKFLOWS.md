# 03 核心业务流程

## 1. 菜单和包厢初始化

首次启动时，如果相应数据表为空，服务端会自动创建：

- 三个示例分类/菜品；
- 两个示例包厢；
- 每个包厢的随机二维码 token；源码仍会填充已退役的 Access Code 兼容字段；
- 场所名称、地址、电话和隐私模式设置；
- 默认员工账号。

若 SQLite 还没有菜单、包厢和订单，但 `database/store.json` 存在，系统会优先尝试把旧 JSON 数据迁移到 SQLite。

## 2. 管理员配置菜单

经营管理页支持：

1. 新建、改名、排序和删除分类。
2. 新增、编辑、上下架、选择删除和全部删除菜单项。
3. 从结构化文本批量导入菜单。
4. 保存时由服务端统一规范名称、价格、描述、分类和排序。

菜单项包含名称、价格、描述、分类、排序和是否可用。顾客上下文会收到所有菜单，但只有 `available = true` 的项目允许进入有效订单；员工加菜接口同样只接受上架项目。

## 3. 建立桌台/包厢二维码

管理页可以单个或批量建立区域。每个区域保存：

- 内部 ID；
- 对外显示标签；
- 长期随机 token；
- 已退役的 Access Code 兼容字段；
- 完成状态和创建时间。

二维码内容是 `${PUBLIC_BASE_URL}/o/<token>`。扫描后，服务端重定向到顾客页面并把 token 放进查询参数。

“重新生成二维码”会更换 token，因此旧二维码失效。当前后端仍保留 Access Code 轮换接口，但目标前端不得展示或调用；本次也不得删除该后端兼容接口。

## 4. 员工登录

员工使用用户名和密码调用登录接口。服务端对输入密码做 SHA-256 后与数据库值比较，成功后创建随机员工 session。客户端把 session token 放入 `X-Employee-Session` 请求头。

员工会话默认有效 720 分钟，并在每次有效请求时延长，因此属于滑动过期。退出登录和删除员工会撤销相关 session；当前修改用户名或密码不会自动撤销既有 session，这是需要加固的边界。

## 5. 开台

顾客点单前，员工必须调用开台接口。开台会：

- 清空该区域所有实时购物车；
- 清空顾客结算标记；
- 撤销旧顾客 session；
- 重置“已完成”状态；
- 记录新会话周期开始时间；
- 默认使用分开结账模式；
- 把区域标记为已开台。

重复调用已开台区域不会再次清理数据，而是返回 `alreadyOpen = true`。

## 6. 顾客进入与验证

顾客页面首先请求上下文。服务器会返回菜单、分类、区域、是否开台以及当前 session 是否有效。响应中即使仍含 Access Code 兼容标志，目标顾客页也不得显示或据此分支。

建立顾客 session 的条件：

1. 二维码 token 对应有效区域；
2. 区域已经开台；
3. 顾客姓名非空；
4. 目标部署已设置 `ZONE_ACCESS_CODE_REQUIRED=false`，不要求也不接收 Access Code。

成功后服务端创建随机 session token，默认有效 120 分钟。后续购物车和订单请求必须携带 `X-Zone-Session`。

## 7. 多顾客购物车

购物车以 `(zone_id, zone_session_id)` 为主键，因此同一包厢中的不同顾客彼此独立。每个购物车保存：

- 菜单 ID 到数量的 JSON 映射；
- 订单备注；
- 更新时间。

顾客可对单个项目执行 `+1` 或 `-1`，单项最多 99。客户端也会展示同一包厢所有顾客的实时购物车，方便彼此确认。

## 8. 提交订单与金额计算

顾客提交订单时可以发送项目列表，也可以让服务端使用数据库中的当前购物车。服务端不会接受客户端提供的价格，而会：

1. 根据菜单 ID 查找当前菜单。
2. 丢弃不存在、下架、数量无效的项目。
3. 使用服务端菜单价格重新计算每一项小计。
4. 计算订单总额。
5. 在一个 SQLite 事务中写入订单头和明细。
6. 清空该顾客购物车。

金额公式：

```text
subtotal = 所有明细小计之和
serviceCharge = subtotal × 18%
tax = (subtotal + serviceCharge) × 13%
total = subtotal + serviceCharge + tax
```

各步骤按“分”转换并舍入，避免直接累计浮点误差。顾客前端也做相同展示计算，但最终以服务端结果为准。

## 9. 员工接单与订单状态

员工端会定时拉取活动订单。状态集合为：

```text
new -> preparing -> ready -> served
                    \-> cancelled
```

这是界面表达的业务顺序，不是后端强制状态机。当前 API 只验证目标值是否属于允许集合，没有限制必须按相邻状态变化。

员工还可以：

- 标记单个菜品已送/未送；
- 对未完成、未取消的订单增减菜品数量；
- 删除数量减到零的明细，但整单至少保留一件；
- 从当前上架菜单给订单加菜；
- 查看是谁最后处理了订单。

已送菜品不能改数量；`served` 或 `cancelled` 订单不能通过明细接口继续编辑。订单改为 `cancelled` 时，服务端会把明细小计和订单总额归零。

## 10. 分开结账和合并结账

每个区域会话周期有一个结算模式：

- `split`：按顾客分别出单。
- `merged`：把整个区域的非取消订单合并出单。

在 `split` 模式下，服务端从当前会话订单中提取不同顾客姓名，为每人保存 `settled` 标记。只要还有顾客未结，就阻止结单清零。

在 `merged` 模式下，结单守卫不要求逐个顾客标记，整房账单可以直接进入结单流程。

## 11. 小票生成与打印

服务端根据当前区域会话生成小票：

- 分开模式仅汇总指定顾客的非取消订单；
- 合并模式汇总整个区域的非取消订单；
- 同名、同价菜单项会被聚合；
- 重新计算小计、服务费、税和总额；
- 记录打印次数、员工、包厢、时间和订单 ID。

打印流程有两种实现层次：

1. 员工请求打印，服务端把小票 JSON 写入 `print_jobs`，状态为 `pending`。
2. Windows 客户端使用唯一 worker ID 领取一条任务，将其改为 `processing`。
3. Electron 主进程生成小票 HTML，调用系统打印机静默打印。
4. 客户端回报 `completed` 或 `failed`。

服务端领取任务使用 SQLite 事务，避免同一个任务同时被两个打印工作端领取。

## 12. 结单清零

结单前服务端检查：

- 区域仍然开台；
- 分开模式下所有顾客已经标记结清，或当前为合并模式。

通过后：

1. 把 `orders` 复制到 `order_history`。
2. 把 `order_items` 复制到 `order_history_items`。
3. 删除活动订单和明细。
4. 清空该区域所有购物车与结算标记。
5. 撤销全部顾客 session。
6. 目标部署设置 `ROTATE_ACCESS_CODE_ON_CHECKOUT=false`，不轮换已退役的 Access Code 兼容字段。
7. 重置会话周期和结算模式。
8. 把区域标记为未开台。

历史表保存当时的名称、价格、区域标签和处理员工快照，因此之后修改菜单不会改变已归档订单。

## 13. 日结查询

管理页按浏览器日期和时区偏移查询当天数据。后端会合并活动订单和历史订单，按 `createdAt` 过滤，返回：

- 订单数量；
- 总金额；
- 各状态数量；
- 订单明细；
- 数据来源是活动区还是历史区。

取消订单金额在取消时被归零，因此不会以原金额进入当前合计。
